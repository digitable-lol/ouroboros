# Языки

| язык | как добывается трасса | имена доводов |
|---|---|---|
| Python | обмазка исходника | читаются из подписи |
| JavaScript / TypeScript | обмазка исходника | **задаются вручную** |
| C | обмазка исходника, разбор через `libclang` | **задаются вручную** |
| C++ | обмазка исходника, разбор через `libclang` | в навыке не описано — задавайте вручную |
| Elixir | обмазка исходника | в навыке не описано — задавайте вручную |
| **flang** | **обмазка не нужна — записи даёт сама машина flang** | пока не пишутся, см. ниже |

## Одна схема, разные диалекты

Это первое, что стоит понять про пять языков, и это **решение, а не недоделка**.

Все пять пишут в один файл `debug.info` **побайтово одинаковую схему**: те же
ключи, те же две строки на вызов, тот же смысл каждого поля. Иначе слова
«межъязыковая запись» ничего не значили бы. Разбор трассы у вас один на все
языки.

А вот **диалекты** нарочно оставлены родными. Из контракта логгера, дословно:

> Диалекты **нарочно не сводятся к одному**: как язык изображает значение, как
> пишет полное имя, как печатает число — родная форма каждого. Сверка разбирает
> обе трассы и сравнивает записи, убрав диалект.
>
> **Закрепляй схему, а не диалект.**

Три места, где диалекты расходятся:

| что | как расходится |
|---|---|
| изображение значения | Python пишет строку как `'x'`, JS — как `"x"` |
| полное имя функции | Python `Outer.<locals>.add`, JS просто `add`, C++ `Class::method` |
| печать числа `d` | одно и то же значение: Python `1e-06`, JS `0.000001` |

Практический вывод для того, кто пишет разбор трассы: **сравнивать записи разных
языков в лоб нельзя** — сначала убирают диалект, потом сравнивают. Схема при этом
одна, и на неё опираться можно.

## Что каждый язык кладёт в необязательные поля

`ci` (номер ядра) и `th` (метка потока) необязательны: часть, которая не может
получить их дёшево, их не пишет, и разбор читает отсутствие или `-1` как
«неизвестно». *По контракту логгера:*

| язык | номер ядра `ci` | метка потока `th` | монотонные часы для `d` |
|---|---|---|---|
| Python | `os.sched_getcpu()` на Linux; иначе `-1` | `"<pid>.<номер потока>"` | `perf_counter` |
| JavaScript / TypeScript | `-1` | `"<pid>.<номер рабочего потока>"` | `hrtime` |
| C (в ядре системы) | `cpu_index(curcpu())` | `"<pid>.<lid>"` | `getnanouptime` |
| C (обычный) | `-1` | pid | — |
| C++ | `-1` | `std::this_thread::get_id()` | `steady_clock` |
| Elixir | номер планировщика | `inspect(self())` | `monotonic_time` |

`-1` здесь не «ошибка», а честный ответ: переносимого устойчивого номера ядра в
этих средах нет, и выдумывать его не стали.

**У C нет исключений**, поэтому в его записях никогда не бывает поля `x` — только
`r`. Ещё одна особенность C и C++: они собирают строку JSON сами, не подключая
библиотеку, — чтобы сборка для ядра системы не тянула лишнего.

## Откуда берутся имена доводов

Это самая частая причина, по которой у человека «ничего не добылось», поэтому
стоит понять устройство, а не запомнить правило.

В самой записи имён позиционных доводов **нет по устройству**. Поле `a` — это
значения через запятую, и только значения. Имена есть лишь у именованных доводов
(поле `k`, вид `имя=значение`), а в языках, где именованных доводов не бывает,
`k` пустое.

Значит имя каждому позиционному доводу мост должен взять откуда-то ещё, и мест
всего два: **подпись функции, прочитанная из исходника**, или **явный список**.

Навык называет только эти два источника, и подпись он читает из исходника Python.
Про TypeScript и C сказано прямо, что подписи **не читаются**. Про C++ и Elixir
не сказано ничего — поэтому здесь стоит «не описано», а не «читаются». Разница
существенная: во втором случае правду вы узнаете из отказа, а не из документации.

Там, где имена не читаются, их передают списком — в навыке этот довод назван
`param_names`. Иначе записи будут отброшены с причиной `no-parameter-name`: имя
`арг1` не выдумывается.

> Контракт логгера мимоходом называет ещё и форму полного имени для C#
> (`Тип.Метод`). Списком поддерживаемых языков это не является: и навык, и сам
> контракт перечисляют одни и те же пять — Python, JavaScript/TypeScript, C, C++,
> Elixir.

## flang — особый случай

> **Откуда это известно.** flang в навыке про уроборос **не описан вовсе**: там
> перечислены пять языков, и flang среди них нет. В контракте логгера его тоже
> нет — контракт перечисляет те же пять. Всё в этом разделе — замысел владельца
> проекта и свойства самого flang, а не снятое с работающего моста поведение.
> Читайте раздел как план работ, которым он и является.

У пяти языков инструмент **переписывает исходник**, вставляя записи о входе и
выходе. У flang этого делать не нужно вовсе.

**Причина первая: записи уже есть.** Через одну функцию исполняющей машины flang
(её называют рантаймом) проходит каждый вызов, способный к рекурсии, и там уже
видно имя, глубину и число шагов. Режим
записи включается переменной среды и ничего не переписывает:

```sh
FLANG_WATCH=/tmp/hod.txt FLANG_PULSE=5000000 flang check файл.flang
```

Остаётся добавить доводы — и трасса готова, без обмазки, без черновика и без
риска, что обмазанный код куда-то уедет.

**Причина вторая, важнее.** У остальных языков добытый пример надо куда-то
положить — в тесты, в спецификацию, в отдельный файл. В flang **пример — часть
языка**, и он не украшение:

> Доказанное утверждение **с примером** снимается из напечатанного кода.
> Без примера — остаётся проверкой при каждом запуске.

То есть добытый из трассы пример не просто документирует поведение, а **делает
программу легче**. Цепочка замыкается буквально:

```
прогнали программу
      ↓
получили примеры из трассы
      ↓
примеры сделали утверждения снимаемыми
      ↓
напечатанный код стал легче
      ↓
программа работает быстрее
```

Змея съедает собственный хвост и становится меньше.

**Причина третья: повторяемость.** В flang нет изменяемого состояния, поэтому
функция вместе с доводами **и есть** полное состояние вызова. Вынули из трассы,
подставили обратно — получили ровно тот же вызов. В языках с изменяемым
состоянием пришлось бы восстанавливать ещё и его, и это ровно то, из-за чего
живую отладку там смотрят «вживую», а не повторяют.

## Что нужно сделать для flang

1. Дописать в записи **доводы вызова**, а не только имя функции. Сегодня
   пишется имя, глубина и счёт вызовов.
2. Научить мост читать этот вид записей — он отличается от обмазочного тем, что
   приходит одним потоком, а не парами «вход/выход».
3. Сохранить общее правило отказов: из трассы берутся **только примеры**,
   правила и свойства — от человека.

Работа небольшая и от обмазки не зависит: обмазывать нечего, канал уже есть.

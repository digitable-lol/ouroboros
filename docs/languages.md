# Языки

Пять языков. Схема записи у всех одна, а способ вставки и мелкие подробности —
разные. Всё в таблицах ниже снято с настоящих прогонов на этой машине, а не
выведено из описания.

| язык | расширения | как вставляется запись | что нужно на машине |
|---|---|---|---|
| Python | `.py` | надстройка `@_ouro_log` над функцией | ничего сверх Python |
| JavaScript / TypeScript | `.js .mjs .cjs .jsx .ts .tsx` | `try/finally` в теле | `node` |
| C | `.c .h` | `__attribute__((cleanup))` | `gcc`/`clang`, чтобы собрать |
| C++ | `.cpp .cc .cxx .hpp .hh .hxx` | сторож области видимости (RAII) | `g++`/`clang++` |
| Elixir | `.ex .exs` | `use Ouroboros.Trace`, переопределение `def` | `elixir` |

`libclang` для разбора C и C++ и `@babel/parser` для разбора JavaScript уложены
внутрь пакета — доставлять их отдельно не надо. Компилятор и `node` нужны, чтобы
**собрать и запустить** обмазанный код, а не чтобы его обмазать.

Список, который печатает сам инструмент:

```sh
ouroboros languages
```

```json
{"languages": ["python", "javascript", "c", "cpp", "elixir"]}
```

## Одна схема, разные диалекты

Это первое, что стоит понять, и это **решение, а не недоделка**.

Все пять пишут в один файл `debug.info` одну и ту же схему: те же ключи, те же
две строки на вызов, тот же смысл каждого поля. Разбор трассы у вас один на все
языки.

А вот **диалекты** нарочно оставлены родными. Из [SPEC.md](https://github.com/digitable-lol/ouroboros/blob/main/SPEC.md):

> Диалекты нарочно не сводятся к одному: как язык изображает значение, как пишет
> полное имя, как печатает число — родная форма каждого. **Закрепляй схему, а не
> диалект.**

Проверка `tests/test_cross_language.py` разбирает трассы двух языков и сравнивает
записи, предварительно убрав диалект.

### Как пишется полное имя

Снято с прогонов:

| язык | что в поле `fn` |
|---|---|
| Python, метод | `Box.put` |
| Python, вложенная функция | `outer.<locals>.inner` |
| C++, метод | `Calc::add` |
| C | `add` |
| JavaScript | `mul` |
| Elixir | `add` — **без имени модуля** |

### Как изображается значение

Python пишет строку как `'мир'`, JavaScript — как `"мир"`. Одна и та же
длительность у Python выглядит как `1e-06`, у JavaScript — как `0.000001`.
Сравнивать записи разных языков в лоб нельзя: сперва убирают диалект.

## Откуда берутся имена доводов

Здесь языки расходятся сильнее всего, и это надо знать заранее.

| язык | поле `a` (по позиции) | поле `k` (именованные) |
|---|---|---|
| Python | **только значения**: `'мир'`, `[1, 2]` | `greeting='здравствуй', loud=True` |
| JavaScript | **только значения**: `2, 3` | пусто |
| C | **с именами**: `a=2, b=3` | пусто |
| C++ | **с именами**: `a=2, b=3` | пусто |
| Elixir | **с именами**: `a=2, b=3` | пусто |

Причина разная у двух половин таблицы. У Python и JavaScript запись делает
помощник **во время работы программы**, а туда доводы приходят уже без имён —
одними значениями. У C, C++ и Elixir строка записи собирается **при обмазке**, то
есть тогда, когда подпись функции разобрана и имена известны; они и вписываются
прямо в запись.

Отсюда практический вывод: у Python и JavaScript имя позиционного довода из
записи не восстановить — смотрите подпись в исходнике. Именованные доводы Python
пишет с именами всегда.

## Ядро, поток и часы

`ci` (номер ядра) и `th` (метка потока) стоят в строке входа. Снято с прогонов:

| язык | `ci` (ядро) | `th` (поток) | часы для `d` |
|---|---|---|---|
| Python | всегда `-1` | `3022740.135295175909888` (`<процесс>.<поток>`) | `perf_counter` |
| JavaScript | `-1` | `2868765.0` | `hrtime` |
| C (обычный) | `-1` | `2869044` (номер процесса) | — |
| C (в ядре системы) | `cpu_index(curcpu())` | `<pid>.<lid>` | `getnanouptime` |
| C++ | `-1` | `123177861400448` | `steady_clock` |
| Elixir | **`5`** — номер планировщика BEAM | `#PID<0.95.0>` | `monotonic_time` |

> **Про `-1` у Python.** В помощнике стоит попытка позвать `os.sched_getcpu()`, а
> при её отсутствии — вернуть `-1`
> ([`ouroboros/runtime.py:65`](https://github.com/digitable-lol/ouroboros/blob/main/ouroboros/runtime.py#L65)).
> Такой функции в CPython нет вовсе — проверено на 3.12.13 и 3.14.4 под Linux, —
> поэтому у Python поле `ci` **всегда** `-1`, а в разборе — `null`. Настоящий
> номер ядра приходит только от записи в ядре операционной системы на C, а у
> Elixir в этом поле номер планировщика.

`-1` здесь не «ошибка», а честный ответ «неизвестно»: переносимого способа узнать
ядро в этих средах нет, и выдумывать его не стали.

**У C нет исключений**, поэтому в его записях никогда не бывает поля `x` — только
`r`. Ещё одна особенность C и C++: они собирают строку JSON сами, не подключая
библиотеку, — чтобы сборка для ядра системы не тянула лишнего.

## Что каждый язык умеет и чего не умеет

**Python.** Самый обкатанный из пяти. Надстройка ставится **ближе всего к
`def`**, то есть внутрь всех прочих надстроек, и записывает саму функцию. Тело не
трогается — поэтому несколько `return`, ранние выходы, вложенные функции и уже
написанный `try/finally` продолжают работать. `lambda` пропускается. Строка
описания модуля и `from __future__ import` остаются первыми, как того требует
язык (обе поломки чинились здесь и закрыты проверками).

**JavaScript / TypeScript.** Стрелочные функции с коротким телом (`x => x + 1`)
пропускаются — это то же решение, что и пропуск `lambda` у Python. Асинхронные
функции записывают возвращённое обещание, а не то, во что оно разрешится.
Помощник ищется рядом с файлом.

> **Известная поломка: пропадает строгий режим.** Строка ввоза помощника
> вставляется выше `"use strict"`, и директива, переставшая быть первой,
> перестаёт действовать. Программа продолжает работать — иначе, чем работала.
> Проверено прогоном; разбор — в
> [Границах](limits.md#где-обмазка-меняет-поведение-программы).

**C.** Запись ставится на любой выход — `return`, `goto`, конец тела. Вид довода
подбирается по разобранному типу (`%d`, `%ld`, `%p`, `%s` с проверкой на пустой
указатель). Есть отдельный облегчённый вид записи для горячих и рекурсивных
функций — `--minimal`: без хранения кадра вызова, только имя и глубина. Он
рассчитан на сборку для ядра операционной системы.

**C++.** Значение изображается через `operator<<`, если он есть. Выход по
исключению отличается от обычного через `std::uncaught_exceptions`. Имя пишется
полным — `ns::Class::method`.

> **Известная поломка: возврат списком в скобках.** `return {1, 2, 3};`
> превращается в код, который компилятор не принимает. Ошибка шумная — сборка
> падает, — но обмазать такой файл сейчас нельзя. Проверено прогоном; разбор — в
> [Границах](limits.md#где-обмазка-меняет-поведение-программы).

**Elixir.** `use Ouroboros.Trace` переопределяет `def` и `defp`, поэтому каждая
ветвь функции обмазывается отдельно; охранные выражения и значения по умолчанию
проходят насквозь, доводы берутся из `binding()`, `raise`/`throw`/`exit`
перехватываются. **Порядок сборки важен:** модуль записи должен быть собран
раньше любого модуля, который его использует.

## Работа для ядра операционной системы

Заголовок для C умеет собираться внутри ядра: вместо обычной записи в файл — свой
кольцевой буфер, `printf(9)`, `getnanouptime(9)`, уменьшенный кадр вызова и
защита от повторного входа. Порождаемый код при этом **один и тот же** для обоих
случаев.

Проверено на NetBSD 11.0_RC4 riscv64: пробный модуль ядра с этим заголовком
**собирается начисто** против настоящих заголовков ядра с полным набором ключей
(`-ffreestanding -nostdinc -D_KERNEL -Werror -Wsystem-headers`). Запуск в
пользовательском ядре rump на riscv64 **не получился** — загрузчик модулей rump
не умеет перемещения для riscv64 (`panic: kobj_reloc: not supported on this
architecture`), и это не про наш код. Безопасность при работе — по стеку,
повторному входу и объёму — **остаётся непроверенной**. Подробности — в
[ARCHITECTURE.md](https://github.com/digitable-lol/ouroboros/blob/main/ARCHITECTURE.md).

Общий ринг на несколько единиц трансляции работает: проверка
`tests/test_c.py::test_shared_ring_across_two_tus` собирает два файла в один
кольцевой буфер и получает вложенность, пересекающую границу файла:

```
=== ouroboros ring dump: 2 records (total seen 2) ===
{"p":"in","dep":0,"ci":0,"fn":"fa"}
{"p":"in","dep":1,"ci":0,"fn":"fb"}
=== ouroboros ring end ===
```

## C# — не подключён

`SPEC.md` мимоходом называет форму полного имени для C# (`Тип.Метод`), а
`design/prompt.md` — исходное задание — перечисляет C# среди целей. Разбора для
него **нет**: в списке языков его нет, расширение `.cs` ничему не соответствует.

## flang — не поддерживается

flang в инструменте не упоминается **ни разу**: его нет ни в списке языков, ни в
[SPEC.md](https://github.com/digitable-lol/ouroboros/blob/main/SPEC.md), ни в
исходнике. Обмазать файл flang нельзя — расширению не соответствует ни один
разбор.

Замысел поддержать flang у проекта есть, и он не про обмазку: у flang через одну
функцию исполняющей машины проходит каждый вызов, способный к рекурсии, так что
записи можно брать оттуда, ничего не переписывая. Но это план работ, а не
свойство инструмента, и описывать его здесь как возможность было бы неправдой.

Переменные `FLANG_WATCH` и `FLANG_PULSE`, если вы про них слышали, — устройство
самого flang. К уроборосу они отношения не имеют, и он их не читает.

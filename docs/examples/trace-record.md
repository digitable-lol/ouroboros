# Запись трассы

## Что известно

| про запись | что сказано в навыке |
|---|---|
| куда пишется | в файл `debug.info`; путь задаёт переменная среды `OUROBOROS_DEBUG_INFO` |
| как устроен файл | JSONL — по одной законченной записи в строке |
| сколько записей на вызов | две: на вход и на выход |
| какие поля названы | одно: `d` — длительность |
| предел длины значения | 200 знаков; что длиннее, отбрасывается с причиной `truncated-repr` |

## Чего не известно

**Полный состав полей записи в навыке не описан.** Названо одно поле — `d`.
Остальное — имя функции, файл, доводы, результат, номер вызова — в записи,
очевидно, есть (иначе примеры не собрались бы и прослеживаемость была бы
невозможна), но **как эти поля называются, здесь не написано и додумываться не
будет**.

Отсюда практическое следствие: не пишите разбор `debug.info` по догадке.
Посмотрите настоящую запись — для этого есть операция `read_trace`.

## Чего в записи нет по устройству

**Веток, в которые не заходили.** Трасса описывает прогон, а не программу.

**Намерения.** Функция вернула `-1` — это код ошибки или настоящий ответ? В
записи этого нет.

**Настоящей цены вызова.** Поле `d` меряет время обмазанного прогона. Обмазка
время меняет (результаты — нет), поэтому читать `d` как стоимость обычного
прогона нельзя.

## Что делает предел в 200 знаков

Длинное значение не обрезается «как-нибудь» и не восстанавливается по остатку:
запись, упёршаяся в предел, до примера просто не доходит — она попадает в отказы
с причиной `truncated-repr`. Это и есть общее правило моста: лучше ничего, чем
похоже на правду.

Соседний случай — `unparseable-repr`: `<Foo object at 0x…>` записано, но это
тождество объекта, а не его значение. Такое тоже отбрасывается.

Полный перечень причин отказа — на странице [Границы](../limits.md).
